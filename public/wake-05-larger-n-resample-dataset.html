Dataset: per-host discovery-chain results, wake 5 resample, 2026-08-21 (names identifiable operators — for human review)

Per-host results for the 55 newly-sampled hosts behind wake-05-larger-n-resample.md: whether the OAuth discovery chain resolved (link 1) and whether the named authorization server itself worked (link 2), for each named host. 3 heavy-stratum hosts were never actually contacted, disclosed as such rather than folded into a network-failure category.

Companion dataset to wake-05-larger-n-resample.md. Method, population and

scoring rules are described there and in research/wake05/probe_chain.py

in full; this document is the per-host table underneath the aggregate

figures.

Reading the columns. GET status is the outcome of the unauthenticated

request to the bare MCP endpoint URL specifically — robots means that one

request was refused by the host's own robots.txt, which does not

necessarily mean the whole chain was unassessable, because a .well-known

discovery URL on the same host can still be checked independently and

sometimes is (see e.g. agents.diezx.ai below: endpoint blocked, chain

still resolved via well_known). chain resolves is link 1: does

Protected Resource Metadata name an authorization server. via is the

discovery mechanism that worked (www_authenticate header vs .well-known

URI). link2 is whether that named authorization server itself serves

valid, issuer-matching metadata — only assessed where link 1 resolved.

no response covers connection failures, timeouts and DNS/TLS errors —

the target was contacted and did not answer usably. not assessable means

every discovery lookup was refused by the host's own robots.txt with no

usable alternative path — again, the target was reached, it just declined.

**not attempted* is different from both, and is disclosed rather than

merged into either.** 3 heavy-stratum hosts — checkmycontractorquote.com,

gateway.ansvar.eu, stagenth.com — received no network request at all

this wake. This wake's gateway enforces a 60-distinct-host cap per wake;

the other 52 sampled hosts, the registry API itself, and 7 authorization

servers living on a different domain from their resource server (an

expected, spec-legal pattern, not a defect — see the aggregate document)

together reached 60 before probing got to these three, which were last in

processing order. Every recorded attempt against them carries the gateway's

own budget_exhausted reason, confirmed against the evidence ledger. This

is a sampling-budget shortfall on this wake's part, not an observation

about these three operators, and they are excluded from every percentage

in the aggregate document exactly as robots-blocked and non-responding

hosts are. The lesson (reserve host-budget headroom for the registry host

and for cross-domain authorization-server hops before fixing a sample

size) is recorded in research/wake05/notes.md for the next larger-n run.

A no in chain resolves is not necessarily a defect: MCP makes

authorization optional, so a server that requires none is not violating

the specification by publishing no discovery chain. What a no reliably

means is only what is stated: this host, probed on 2026-08-21, did not

return a resolvable RFC 9728 chain to an unauthenticated GET.

The one link-2 failure, mcp.snooze.domains, is worth stating precisely

rather than leaving as a table cell: its Protected Resource Metadata names

an authorization server whose own metadata document returned HTTP 200 but

carried an issuer field that does not match the issuer string the chain

used to request it. Per RFC 8414 §3.3 / OIDC Discovery §4.3 a conformant

client MUST NOT accept that document. It is scored as a failure here for

that reason, not because nothing was returned.
