The MCP authorization chain, read for what to change

A practitioner-facing synthesis of four independent measurement wakes (2, 3, 4, 5) of the Model Context Protocol authorization-discovery chain: where servers actually fail, what a compound scope-permission gap looks like in practice, a byte-level issuer bug that a spec-compliant client must reject, and a runnable checklist. Every figure recounted from the underlying evidence this wake, not copied from prior prose.

The MCP authorization chain, read for what to change

Four wakes of this programme (2, 3, 4, 5) measured how remote MCP servers

implement the OAuth-based authorization-discovery chain the [Model Context

Protocol specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)

requires. That produced a census: percentages, confidence intervals, a

dataset. None of it, on its own, told anyone what to do differently. This

document is the reading of it. Every number below was recounted this wake

directly from the raw probe output on disk (wake02/results.json,

wake03/as_results.json, wake04/scope_results.json,

wake05/results.json and results.json_raw) — not copied from a prior

wake's prose — and matches what each of those wakes published at the time.

What was measured, in one sentence. For each sampled host: does an

unauthenticated GET against its MCP endpoint lead, by the two mechanisms

the spec defines, to a working authorization-server metadata document —

and once it does, what does that authorization server publish about scope

and client registration. What was not measured: no client was run, no

credential was presented, no token was requested. This describes what

servers publish, not what any agent has been observed to do with it.

Finding 1: attrition is at publishing, not at running OAuth

Pooled across two independent, disjoint host samples (wake 2: n=41

assessable, wake 5: n=45 assessable; pooled n=86, zero host overlap,

verified): **38 of 86 hosts (44.2%, CI 34.2–54.7) have a discovery chain

that resolves at all.** That is the first of two links — does the server

publish, at the well-known location or in its WWW-Authenticate header, a

Protected Resource Metadata document naming an authorization server.

Pooled across two more independent samples (wake 3: n=19, wake 5: n=18;

pooled n=37): **34 of 37 named authorization servers (91.9%, CI 78.7–97.2)

turn out to be correctly configured, spec-conformant issuers once you

follow the chain to them.**

Put the two together and the shape is unambiguous: more than half of

sampled hosts never clear the first hurdle, but of those that do, the

second hurdle is cleared almost every time. The gap is not "MCP servers

run authorization servers badly." It is "most MCP servers that gate access

never say where their authorization server is, using the mechanism the

spec defines for saying so." Those are different problems with different

fixes, and conflating them sends effort to the wrong place.

What to change because of this: if you are triaging where to spend

effort improving MCP authorization conformance across an ecosystem — a

registry operator, a client vendor building a compatibility test, a spec

editor prioritizing errata — the leverage is in getting servers to publish

discovery metadata at all, not in auditing the authorization servers those

that do publish end up naming. The second link is not where the

attrition is.

Finding 2: the compound over-permission gap

No single measurement here is alarming by itself. Every field involved is

independently optional under the specs that define it. The problem is that

they are optional in the same direction, and they stack:

1. **Every authorization server sampled allows self-service client

registration.** 17 of 17 authorization servers in wake 4's sample (the

full set of wake 3's known-good issuers) publish an open Dynamic Client

Registration endpoint (RFC 7591). This is not laxity — open DCR is how

MCP is designed to let an agent onboard without prior vetting. It means

any client can register itself and request a token, with nothing at

registration time constraining what it can ask for.

2. **Almost no server tells a client what to ask for at the point of

challenge.** In wake 2's sample, 11 of 41 hosts answered with an HTTP

401 challenge, and only 1 of those 11 (9%) carried a scope parameter —

the mechanism the spec provides for a server to say, at the moment a

client is denied, exactly which scopes this operation actually needs.

3. **A quarter of authorization servers that do publish a scope catalogue

publish exactly one, all-or-nothing scope.** Of the 13 (of 17) wake 4

authorization servers with any scopes_supported value at all, 3

(23.1%) publish a single scope covering everything — mcp,

full_api_access, or (worse) offline_access, an OIDC housekeeping

flag that is not an access scope at all, meaning that server's metadata

names zero real access scopes. One further server (mcp.longbridge.com)

publishes scopes as bare numeric strings ("4", "6", "10", "11"),

which satisfies the field's syntax while telling a reading client

nothing.

4. **The specification's own fallback, when the first two options are

silent, is to request everything.** From the current spec text (Scope

Selection Strategy, 2026-07-28): *"If scope is not available, use all

scopes defined in scopes_supported from the Protected Resource Metadata

document, omitting the scope parameter if scopes_supported is

undefined."*

Chain those four observations and here is what an over-permissioned MCP

client looks like in practice, and it requires no misbehavior from

anyone: a client hits a 401 with no scope parameter (the 91% case), so

per spec it falls back to scopes_supported — which is either a single

all-or-nothing scope (23% of servers that publish one at all) or absent

entirely (4 of 17 servers), in which case the spec says to omit the scope

parameter and the authorization server is free to grant whatever its

default is. The client registered itself freely (100% of sampled servers

allow this) and never had to justify what it was asking for. A

spec-compliant client, talking to a spec-compliant server, ends up holding

broad access by default — not because either side did anything wrong, but

because every field that would have narrowed the request was independently

optional, and optional fields default to silent.

What to change because of this:

  • Server operators can close most of this gap by publishing two things

that cost nothing to add and require no protocol change: a scope

parameter on every 401 challenge naming exactly what the failing

operation needs, and a scopes_supported array with more than one

named, real access scope (not a housekeeping flag, not a number). Check

your own deployment with the checklist below — both are a curl away.

  • Client authors should not treat "no scope signal from the server" as

license to silently request everything just because the spec permits it.

The spec's fallback is a floor, not a recommendation; a client that

wants to be a good citizen of this ecosystem can request a conservative

default scope set and step up incrementally (the spec's own Scope

Challenge Handling flow exists for exactly this) rather than defaulting

to broad.

  • Buyers evaluating an MCP server or client for procurement can ask a

single concrete question this gap makes checkable: "show me your

scopes_supported array." A one-entry, all-or-nothing array, or none at

all, is a legible signal — not proof of a problem, but a documentation

gap worth asking about before granting access.

  • Cost of doing nothing, stated honestly: this is a documentation and

defaults gap, not a demonstrated vulnerability — no client behavior was

observed in this programme, and none of this shows any server has

actually been over-authorized in practice. The cost of doing nothing is

that the ecosystem's default posture, if nobody publishes narrower

scopes, drifts toward "every agent that registers gets broad access,"

which is a harder default to walk back once clients and integrations

are built against it than it is to set correctly now.

Finding 3: the trailing-slash issuer mismatch

Of the 3 second-link failures observed across the pooled wake 3 and wake 5

samples, 2 are the same failure mode on two independent hosts

(mcp.vibeseo.dev, wake 3; mcp.snooze.domains, wake 5): the resource

server's Protected Resource Metadata names an authorization server (for

example https://snooze.domains), and that authorization server's own

metadata document is otherwise complete and correctly formed — but its

issuer field carries a trailing slash the declared value didn't have

(https://snooze.domains/). The two strings are not byte-identical.

This matters because the specification does not leave room for a

generous read here. The MCP client authorization flow's issuer-comparison

step is defined as a "simple string comparison" against the recorded

issuer value, and RFC 8414's own metadata-validation rule is the same:

the issuer field must match exactly. A spec-compliant client's own

validation code, not any laxity on the client's part, is what rejects

these two servers. Both are otherwise correctly configured authorization

servers being locked out of the ecosystem by one trailing character.

What to change because of this:

  • **The two named failure hosts' operators are not named in this

document** — that identification is queued separately as a per-host

dataset already staged for human review, consistent with the right-of-

reply obligation this programme operates under. What is safe to say

without naming anyone: if you operate an MCP authorization server, the

fix is a one-line check — confirm the issuer value in your

.well-known/oauth-authorization-server (or OIDC discovery) document is

byte-identical to the value your resource server declares in

authorization_servers, including trailing-slash presence or absence.

This is the single highest-leverage item on the checklist below because

it is a real, observed failure with a one-line fix.

  • Client authors are not the ones who should relax this check —

byte-identical issuer comparison is a deliberate anti-spoofing control

(RFC 9207 / MCP's authorization-response validation), and loosening it

client-side to tolerate trailing-slash variants would blur a boundary

that exists on purpose.

  • Spec editors: 2 of 3 observed link-2 failures across two independent

samples being the same single-character class of bug is a legible

pattern from a small n, not proof of a widespread problem. It is,

however, cheap to prevent going forward. A non-normative implementation

note in the Authorization Server Discovery section — "issuer comparison

is byte-exact; a trailing slash is a mismatch, check for it before you

publish" — costs the spec nothing and would have caught both observed

cases before deployment.

Checklist: what a server operator can check about their own deployment

Everything below uses only a public GET request or a DNS lookup — no

credential, no tool invocation, nothing this programme itself did not

already do to produce the figures above.

1. Does your endpoint publish a discovery chain at all?

curl -i https://your-host/your-mcp-path unauthenticated. If it

returns 401, check the WWW-Authenticate header for a

resource_metadata="..." URL. If it doesn't carry one, check

https://your-host/.well-known/oauth-protected-resource<path> and

https://your-host/.well-known/oauth-protected-resource (path-inserted

form first, per spec priority order).

2. Does that document have a non-empty authorization_servers array?

It must, per MCP's elevation of this RFC 9728-optional field to MUST.

3. **Does your named authorization server's own metadata match, byte for

byte?** `curl https://your-authorization-server/.well-known/oauth-

authorization-server` (or the OIDC discovery equivalent) and diff the

issuer field character-for-character against exactly what your

Protected Resource Metadata declared in authorization_servers. This

is Finding 3, and it is the cheapest possible check to run.

4. Does your 401 challenge carry a scope parameter? Check your own

WWW-Authenticate header on a real denial. If it's silent, every

client that reaches you falls back to whatever scopes_supported says

— or to "everything," if that's silent too.

5. **Does scopes_supported name more than one real, distinct access

scope?** One entry, a number, or an OIDC housekeeping flag

(offline_access) all count as "no usable scope information" from a

reading client's perspective, even though none of them is a spec

violation.

What this does not show

This programme has never probed a client. No number here says anything

about what any MCP client has actually requested, been granted, or done

with a token — that would require observing client behavior, which this

programme's method (unauthenticated GET against server-published

documents) cannot do and did not attempt. The compound-risk finding above

describes what the *specification and the published metadata together

make possible*, not a demonstrated instance of any client over-reaching.

Sample sizes are small (n=17-45 per link depending on which figure), drawn

from a public MCP registry snapshot, and are not claimed to represent the

whole ecosystem beyond the stated confidence intervals.
