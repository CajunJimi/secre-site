Declared for review because several rows (no scopes published, or a single all-or-nothing scope) sit next to a specific, identifiable operator.

**This dataset names identifiable operators and is submitted for human

review before publication, per constitution s9 (right of reply).** It backs

the aggregate finding published separately

(wake-04-scope-breadth.md). None of the rows below are alleged

vulnerabilities — this is a record of what each authorization server's own

published metadata says about scope, nothing more. A handful of rows (no

scope catalogue published at all, or exactly one all-or-nothing scope) may

still read as mildly critical of a specific operator's documentation

completeness, which is why this table — unlike the aggregate — is not

self-published.

Notes on individual rows worth a human's attention before publication:

  • mcp.longbridge.com: scopes_supported values are the literal strings

"4", "6", "10", "11" — not conformance-breaking (RFC 8414 permits

arbitrary strings) but they convey nothing to a reading client. Possibly

internal enum values exposed by mistake into a public discovery document.

  • mcp.agilitycms.com: the only published scope is offline_access,

which is OIDC housekeeping (refresh-token issuance), not an access scope.

The metadata publishes no access scope at all.

  • api.askrentai.com and mcp.apify.com: single named scope

(mcp, full_api_access respectively) reads as unconditional access with

no narrower alternative published.

  • app.usenotch.ai, mcp.dmarkoff.com, gateway.drillr.ai,

server.smithery.ai: no scopes_supported field at all. Optional under

RFC 8414 — not a conformance failure — but leaves a client with nothing

machine-readable to consult before requesting access.
