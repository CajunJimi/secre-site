MCP's new UI extension names its own attack scenario, then ships a CSP that allows it

MCP Apps, a new official extension that lets MCP servers render interactive HTML inside a host, names a malicious-HTML threat and calls CSP enforcement a MUST mitigation. Its own default CSP, its own reference code, and its own reference host implementation all permit inline script execution -- the exact vector its named threat depends on. Its own security test suite does not test CSP at all.

MCP Apps is a new official extension to the Model Context Protocol (SEP-1724, in the modelcontextprotocol/ext-apps repository) that lets an MCP server hand a host interactive HTML to render — dashboards, forms, maps, whatever a tool call wants to show. The current spec text is dated 2026-01-26 and marked Status: Stable.

The spec is unusually direct about the risk. Its "Security Implications" section opens: "Hosting interactive UI content from potentially untrusted MCP servers requires careful security consideration," and its threat model names, first among five scenarios, "Malicious server delivers harmful HTML content." Mitigation 4 against that threat is Content Security Policy Enforcement: "Hosts MUST enforce Content Security Policies based on resource metadata."

I read the CSP the spec actually specifies.

The spec's own restrictive default allows inline scripts. When a server resource does not declare CSP metadata, the spec says hosts MUST fall back to:

default-src 'none';
script-src 'self' 'unsafe-inline';
style-src 'self' 'unsafe-inline';
img-src 'self' data:;
media-src 'self' data:;
connect-src 'none';

'unsafe-inline' in script-src is the specific CSP keyword that permits a <script> tag or an inline event handler embedded directly in a page to execute. It is also the single most common thing a CSP is written to block, because it is the mechanism behind the majority of practical HTML-injection and cross-site-scripting attacks — which is exactly the "malicious server delivers harmful HTML content" scenario the spec names as its first threat. A CSP that still allows inline scripts blocks almost none of that threat. The spec's own worked example for constructing a CSP from a server's declared metadata carries the same 'unsafe-inline' in both script-src and style-src.

It is not a stale draft artifact. The same repository also carries a specification/draft/apps.mdx, the in-progress next version of the spec. It differs from the Stable file in several places — added fields, a bidirectional tools/call clarification, a sampling/createMessage addition — but the restrictive-default CSP and the CSP-construction code both still carry 'unsafe-inline' in script-src, unchanged.

The reference host implementation is looser than the spec's own default. examples/basic-host/serve.ts is the project's example of a working host that actually serves the sandboxed iframe and sets the CSP header. Its buildCspHeader function constructs:

script-src 'self' 'unsafe-inline' 'unsafe-eval' blob: data: <declared resource domains>

— adding 'unsafe-eval', blob:, and data: on top of what the spec itself documents as the restrictive default, with the code comment "some libs need eval." Whatever the practical reason, the effect is a CSP that permits inline script execution, dynamic code evaluation via eval/Function, and script loading from blob:/data: URIs — a policy that, as a mitigation against "malicious server delivers harmful HTML content," blocks very little.

And the project's own security tests do not check any of this. tests/e2e/security.spec.ts is the repository's dedicated security test suite. Its own header comment says it verifies "1. Sandbox proxy - origin validation... 2. Iframe isolation... 3. Communication channels." All of that is real and it does test origin checks and sandbox isolation. But the file contains zero references to CSP, script-src, or unsafe-inline — the mitigation the spec itself lists as a MUST is not exercised by the test suite that exists to catch security regressions in this code.

To be fair to the spec's authors: iframe sandboxing (mitigation 1) is a real, separately-enforced boundary, and CSP here is a second layer, not the only one. Nothing in what I read lets a View iframe escape its sandbox or reach the host directly. What the CSP gap affects is narrower and still real: content injected into the served HTML — by a malicious server, or by unsanitized data a legitimate server includes from elsewhere — can run script inside that sandbox, which is precisely the failure mode mitigation 4 is named to prevent, and precisely the thing the reference implementation's own CSP does not block.

This is the same kind of gap this project has documented before in MCP's Tools spec (a stated "don't trust this field" warning with no client-side code enforcing it) — a security claim that exists in prose but not in the mechanism meant to carry it. MCP Apps is new enough, and honest enough about its own threat model, that this is worth flagging while the spec is still Stable rather than final.
